# ADR-0004：本地优先的数据与缓存策略

- **状态**：已接受（accepted）
- **日期**：2026-10-22
- **决策者**：用户
- **影响域**：GreenDAO 本地库、`GlobalDataHolder`、MMKV 权限/更新频率状态、样式配置与设置文件缓存
- **编号说明**：本编号属本仓 `docs/architecture/adr/` 序列。代码注释中未使用 `ADR-0004` 指代其他仓的决策。

---

## 1. 背景（Context）

应用的核心内容是书籍、章节、药物、方剂与名词解释。当前数据层的事实：

- **本地库**：GreenDAO 3.3 + SQLite，库名 `myzhongyi.db`，schema 版本 2，19 个实体；`DataRepository` / `LocalServices` 提供服务，`DbService` 提供串行执行器与事务入口。
- **内存**：`GlobalDataHolder` 持有导航、药物、名词、别名等热数据；冷启动由 `AppDataInitializer` 从本地库预热。
- **刷新**：`AppDataManager.loadAllDataIfNeeded` 按 `DataUpdateFrequency`（每次启动/每天/每周/每月/手动，默认每周）决定是否重新执行加载序列；每个数据源仍是本地优先，本地有数据就不请求网络。
- **权限**：搜索与名词解释权限由独立端点拉取，进程内 `sFetchOk` fail-closed，失败 30 分钟退避，一次启动只拉一次；MMKV 只保存最近一次状态，网关不读磁盘缓存。
- **样式配置**：文件缓存 `style_config_cache` 保存服务端版本号与配置；启动先读缓存，网络返回同版本则跳过应用/落盘。
- **设置**：`FragmentSetting` 通过 `CacheHelper` 序列化到应用私有文件。

存在的关键问题：

1. “刷新频率到期”被误解为“已获得最新网络内容”，实际本地有数据时不会请求网络；
2. 登录/退出未清理搜索与名词权限状态，同进程切换账号可能沿用旧权限；
3. 内容实体没有版本字段，无法判断单条/单表是否需要更新；
4. 多个缓存各自定义失效策略，缺少统一边界说明。

---

## 2. 决策（Decision）

**维持本地优先架构；以“明确真源、明确失效边界、权限 fail-closed”为原则治理缓存；本轮不引入内容版本化与离线写回。**

具体决策：

1. **真源与读取顺序**
   - 内容读取顺序：`GlobalDataHolder` → 本地 SQLite/文件缓存 → 网络（仅本地为空或显式刷新）。
   - 网络成功后：先更新内存，再经 `DbService` 串行异步落库；落库失败保留旧数据并记录日志。
   - 主线程禁止数据库操作。

2. **刷新语义**
   - 保留 `DataUpdateFrequency` 五种模式与默认 `WEEKLY`。
   - 当前“到期重载”仍按本地优先执行；**真正的网络全量刷新列入 M2**，在实现前文档与代码保持一致，不宣称已具备该能力。
   - `last_update_time` 表示“加载序列完成时间”，不是服务端内容版本。

3. **权限状态**
   - 权限是独立于内容的增量状态：进程内判定、fail-closed、失败 30 分钟退避、一次启动一拉。
   - MMKV 缓存只用于持久化/诊断，不是放行依据；字段缺失按失败处理。
   - **M1 必须补齐登录/退出清理**：重置 `sFetchOk`/`sState`，清除两个权限 MMKV 的 `cache` 与拉取时钟，下次前台重新拉取；退出后立即隐藏依赖权限的入口。

4. **样式配置**
   - 保留文件缓存 + 服务端版本比较；缓存无 TTL，离线继续使用旧配置。
   - 请求参数 `version` 是本地计数器，不是增量游标；服务端每次返回全量配置。
   - 缓存类必须保持 `Serializable` 且显式 `serialVersionUID`。

5. **内容版本化**
   - 本轮**不新增** `version` / `ordinal` / 增量游标字段，不做差量合并。
   - 服务端内容仍按全量快照下发；客户端按范围“先清后写”整表替换。

6. **缓存新增门槛**
   - 任何新缓存必须说明：写入时机、读取时机、失效/清除边界、失败行为、敏感字段处理。
   - 没有失效策略的缓存不得新增；不得为同一数据建第二份平行缓存。

---

## 3. 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 改为网络优先、本地仅作兜底 | 阅读类应用弱网/无网场景多；网络优先会让首屏变慢，且当前内容接口没有增量能力 |
| 立即引入内容版本号/增量下发 | 需要后端协同与契约改造，客户端无法单方面完成；当前全量快照的体量尚可接受 |
| 迁移 Room/DataStore | 迁移覆盖 19 个实体、DAO、迁移与测试，收益主要是开发体验，与本轮目标不匹配 |
| 给权限缓存加 TTL 后直接放行 | 权限必须 fail-closed；TTL 只能减少请求，不能替代“未知即拒绝” |
| 用内容缓存 TTL 控制新鲜度 | 前端 TTL 无法感知服务端变更；会制造“看起来最新”的假象，且与更新频率语义冲突 |
| 登录退出不清理权限，靠下次冷启动 | 同进程切换账号会出现权限串号；这是安全/合规缺口，必须修 |

## 4. 后果（Consequences）

### 4.1 正面

- 弱网/无网仍可读已缓存内容，首屏不依赖网络。
- 权限行为可预测：未知即拒绝，不会因缓存放行。
- 缓存边界集中成文，新增缓存有统一检查项。
- 不承担数据库迁移与后端契约改造风险，M1 可在不改业务行为的前提下推进。

### 4.2 负面 / 风险

| 风险 | 评估与处置 |
| --- | --- |
| 用户以为“自动更新”已拿到最新内容 | 文档明确当前只是重载；M2 实现真正的网络刷新并在 UI 上提供刷新反馈 |
| 权限清理遗漏某个退出路径 | M1 收敛到账号会话边界的唯一入口；测试覆盖登录→退出→换号 |
| 全量替换期间读写并发 | 所有 DB 操作走 `mf-db-serial`；跨表事务；未启用 WAL，禁止并发写 |
| 缓存文件反序列化失败 | `CacheHelper` 删除损坏文件；缓存类显式 `serialVersionUID`；字段变更评估兼容 |
| 内存态与库不一致 | 网络成功先同步内存保证 UI 可用；落库失败保留旧数据并记录，不回滚内存（现有边界，M2 评估） |
| 样式配置长期不更新 | 联网后按服务端版本比较；缓存无 TTL 的问题列入 M3 可观测性治理 |

### 4.3 对现有代码的影响

本 ADR 本身**不修改代码**。后续变更必须遵守：

- 数据层文档 `docs/architecture/data-model.md` 为唯一说明入口；
- M1 权限清理、M2 网络刷新、M3 内容版本化分别独立推进，不得混入同一功能票扩大范围。

---

## 5. 验证与落地

1. 文档与 ADR 同批提交；`docs/README.md` 建立索引。
2. M1：
   - 权限清理逻辑有单元测试（登录/退出/换号）；
   - 权限状态、退避、字段完整性测试通过；
   - 不改变内容刷新行为。
3. M2：
   - 明确“到期后网络刷新”的触发、失败回滚与整表替换；
   - 补列表落库与分页契约。
4. M3：
   - 与服务端协同内容版本号/增量下发；
   - 评估 WAL、索引与启动 IO。
5. 常规门禁：`gradlew.bat testDebugUnitTest`；涉及数据库迁移时补升级测试。
